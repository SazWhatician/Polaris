# Phase 1 — Authentication & Document Management

> **Outcome:** A signed-in user lands on `/dashboard`, uploads a PDF/image directly to Firebase Storage via a backend-signed URL, sees it in their list, and can delete it. Firestore + Storage security rules enforce per-user isolation and are tested against the emulator suite in CI.

## Endpoints

| Method | Path | Auth | Body / Notes |
|---|---|---|---|
| POST | `/api/documents` | Bearer | `{filename, mime_type, size_bytes}` → `{document_id, upload_url, storage_path, expires_in_seconds, required_headers}` |
| POST | `/api/documents/{id}/finalize` | Bearer | empty body → updated `DocumentResponse` |
| GET  | `/api/documents` | Bearer | → `{items, next_cursor}` |
| DELETE | `/api/documents/{id}` | Bearer | 204 |

Upload sequence (interview-defensible):

```
client → POST /api/documents              # validate + persist `requested` + return signed PUT URL
client → PUT  <signed-url>  (to GCS)      # bytes never touch our API
client → POST /api/documents/{id}/finalize # verify blob exists + transition to `uploaded`
client → GET  /api/documents              # render the list
```

## Concepts to internalize (interview-framed)

| Concept | Why it matters in an interview |
|---|---|
| Signed URL pattern for uploads | Classic "design a file upload service" answer; you'll be asked why not proxy — ADR 0003 has your answer |
| Two-phase upload (request → finalize) | State machine on a resource; same shape as Stripe PaymentIntents, S3 multipart uploads |
| `asyncio.to_thread` around sync Firestore client | Async-correctness — don't block the event loop with sync I/O; trade-off is one OS thread per concurrent Firestore call |
| Repository → Service → API layering | Reviewer can verify "no Firestore calls outside `repositories/`" with a single grep |
| Firestore security rules as code + as tests | Defense in depth; you can defend "what happens if a backend bug allows cross-tenant reads?" — the rules still deny |
| Default-deny pattern | Both `firestore.rules` and `storage.rules` end with `match {**} { allow read,write: if false }` — common audit ask |
| Optimistic UI with rollback | The DocumentList shows the pattern: snapshot prev → mutate UI → on failure, restore + toast |
| OpenAPI-driven type generation | One source of truth (the Pydantic models) → JSON spec → TS types; CI fails on drift |
| `dependency_overrides` for FastAPI tests | Idiomatic FastAPI testing pattern — interviewers like seeing it |
| Defensive `_require_owned` check | "Belt and braces" — the path scoping already enforces it, but explicit verification is one more wall |

## Gotchas you'll hit (and the fix)

1. **First push will fail the `openapi-stale-check` CI job.** The committed `schema.gen.ts` is a placeholder. Locally: `just gen-api && git add frontend/lib/api/schema.gen.ts && git commit -m "regen openapi types"`. Subsequent pushes pass until you change a route, at which point CI tells you to regen again.
2. **GCS CORS must be configured on the bucket** before browser PUTs work. One-time setup:
   ```
   cat > cors.json <<EOF
   [{"origin": ["http://localhost:3000","https://YOUR-PROD-DOMAIN"],
     "method": ["PUT","GET","HEAD","DELETE"],
     "responseHeader": ["Content-Type","x-goog-resumable"],
     "maxAgeSeconds": 3600}]
   EOF
   gsutil cors set cors.json gs://polaris-27fd9.firebasestorage.app
   ```
   Without this, the browser blocks the PUT with a CORS error; the backend logs nothing because the request never lands there.
3. **Firebase Storage bucket name may be `<project>.appspot.com` (legacy) or `<project>.firebasestorage.app` (newer).** `backend/.env` defaults to `polaris-27fd9.firebasestorage.app`. If you get `404 Not Found` on signed URLs, check Firebase Console → Storage and copy the bucket name shown there into `FIREBASE_STORAGE_BUCKET`.
4. **Firebase web SDK config must be in `frontend/.env.local`.** Without it, `signInWithPopup` throws immediately. Copy from Firebase Console → Project settings → Your apps → Web → Config.
5. **`useEffect` in `app/page.tsx` runs before `loading` settles** — that's why the redirect waits on `if (user)` not `if (!loading && user)`. Setting both is safer in more complex flows.
6. **Rules tests need Java 17.** Already wired in CI; locally you need a JDK to run `firebase emulators:exec` — `sdkman install java 17.0.13-tem` on macOS/Linux, or download Temurin on Windows.
7. **`asyncio.to_thread` doesn't propagate the OTel context automatically.** For now we're fine — Firestore calls are leaves with no further instrumentation. If we ever wrap an instrumented client with `to_thread`, we'd lose the span lineage. ADR-worthy if it bites.
8. **Admin SDK writes bypass rules.** Your backend tests of the service do NOT exercise security rules; the rules tests do. Don't conflate the two layers.

## What you do next (before saying "start phase 2")

1. **One-time bucket setup** (CORS config above). Required for browser uploads.
2. `cd frontend && npm install` — picks up the new radix/sonner deps.
3. `just up` (or `docker-compose up -d --build` if `just` is grumbling). Backend should report `firebase.initialized` with `mode=service-account` in the logs.
4. `just gen-api` then commit the regenerated `frontend/lib/api/schema.gen.ts` so the CI stale-check goes green.
5. `cd frontend && npm run dev` → sign in → hit `/dashboard` → upload a PDF → see it appear → delete it → see toast.
6. `just be-test` → 23 passing tests (4 from P0 + 9 service + 6 API + the 4 P0 tests that still cover health/auth).
7. (Optional) Run rules tests locally if you have Java: `firebase emulators:exec --only firestore,storage "npm --prefix rules test"`.
8. Commit + push, watch CI go green (after the gen-api commit).

## Known debt / "what I'd do next"

- **No integration tests** that exercise the real Firestore client against the emulator — the unit tests use fakes. Worth adding a single end-to-end test in Phase 3 once the test infra is humming.
- **No pagination yet** — `next_cursor` is plumbed in the response model but always `None`. Trivial to add when the list grows past `document_list_limit` (50). Don't add until needed.
- **No content-hash on finalize** — Phase 2 will need this for OCR idempotency. Plan: read `blob.md5_hash` from GCS metadata at finalize, store as `content_hash`.
- **`backend/.env` is committed-by-Claude convenience.** It's `.gitignore`d so it won't leak, but you should rotate the service account once if anything ever surprises you.
- **Frontend has no tests yet** — Playwright happy-path lands at MVP (Phase 3). For now the UI is validated manually.
- **No rate limiting** on `/api/documents` — `slowapi` lands in Phase 6 alongside the YouTube API.
